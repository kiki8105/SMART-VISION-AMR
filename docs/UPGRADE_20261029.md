# 운용 보완 내용과 시험 방법

실차 성능 수치는 아직 측정하지 않았습니다. 아래는 코드에 적용한 동작이며,
같은 지도·시작 자세·적재·목표로 반복 시험해 실제 설정을 결정합니다.
격리 Gazebo 시험의 합부와 측정값은 [2026-10-29 검증 기록](../benchmarks/upgrade_20261029/README.md)에 있습니다.

## 주행

- A* 경로의 불필요한 굴곡을 줄이고 코너를 완만하게 만듭니다. 새 선분은
  팽창 장애물·미확인 셀·격자 모서리까지 검사합니다. 실패하면 안전한 원래 경로를 사용합니다.
- 추종 중 곡률, 최대 각속도, 횡가속도에 따라 `/speed_limit`으로 Nav2 속도 상한을 보냅니다.
  원래 Nav2에 더 낮은 제한이 있으면 그 값을 유지합니다.
- FollowPath의 요청·피드백·취소·종료 응답을 각각 감시합니다. 취소 미확인 상태에서
  새 명령을 겹치지 않습니다. 목표는 유지하지만 제어 종료 확인을 잃으면 정지를 유지합니다.
- 라이다는 측정 시각 TF로 투영합니다. TF가 늦으면 제한된 대기열에서 재시도하고
  오래된 스캔은 버립니다. `/smart_vision_amr/scan_projection_status`로 이유를 확인합니다.
  스캔 개별 빔의 운동 보정은 아직 포함하지 않습니다.

조절 파일: `ros2_ws/src/smart_vision_amr/config/classroom_hardware_nodes.yaml`
(`path_smoothing_*`, `curve_*`, `follow_*`, `scan_*` 항목의 주석을 확인하세요).
실제 차체 폭보다 작게 팽창 여유를 줄여 통과시키는 방식은 사용하지 않습니다.

## 위치 추정과 실행 구조

실차 기본값은 **로봇에서 독립 바퀴·IMU EKF + 입력/출력 감시 + 최종 속도 중재**,
PC에서 **AMCL·A*·Nav2·웹**입니다. 로봇의 기존 TurtleBot3 워크스페이스는 유지합니다.
Pi에 한 번 `scripts/setup_robot_runtime.sh`를 실행해야 합니다.
이전 PC EKF 구성은 양쪽에서 `SMART_VISION_ESTIMATION_LOCATION=pc`로 되돌릴 수 있습니다.
정확한 명령은 [실차 시작 안내](classroom_navigation_startup.md)를 따르세요.

`localization_health`는 AMCL 공분산, 라이다-지도 일치도, 추정 점프,
실제 `/odom`·TF·센서 신선도를 감시합니다. 초기 위치 미확정은 경고 상태이며
자동주행을 막습니다. 주행 중 신뢰도가 크게 떨어지면 정지를 유지합니다.
센서 수신이 0.5초를 넘겨 오래되면 자동주행을 차단하고, 이상이 추가 0.5초
유지되면 정지를 잠급니다. 감시 주기·메시지 전달 지연이 있으므로 물리적 정지 시간을 뜻하지 않습니다.
복구는 실제 위치 지정 → 센서 안정 확인 → 명시적 비상정지 해제 → 위치 확인 →
별도 임무 재개 순서입니다. 센서가 돌아왔다고 자동 출발하지 않습니다.

EKF는 오차를 없애지 않습니다. AMCL의 지도 보정이 장기 오차를 제한하며,
바퀴 치수·IMU 잡음은 [보정 도구](hardware_ekf.md)의 실측 절차로 결정합니다.
로컬 EKF의 누적 자세 공분산만으로 지도상 위치 실패를 선언하지 않습니다.
로컬 속도 측정의 이상과 AMCL·라이다가 판단한 지도 기준 불확실성을 구분합니다.
AMCL은 정지 중에는 새 자세를 내보내지 않을 수 있습니다. 갱신 지연 감시는
마지막 새 AMCL 수신 이후 실제로 움직인 누적 시간을 사용합니다.
오래 정지한 뒤 첫 저속 회전을 시작한 시점에 과거 정지 시간 때문에 막히지 않습니다.
정지·재출발 반복이나 일반 비상정지 해제로 이 누적 시간을 지울 수는 없습니다.

## 웹·조종기

- 현재 운용 단계, 우선 해결할 문제, 다음 조치, 실제 방문 순서와 마지막 홈 복귀를 표시합니다.
- 센서 상세는 접어서 볼 수 있습니다. 수동 조종·재계획·위치 확인·홈 복귀를 구분합니다.
- 웹과 PyQt가 같은 비상정지/해제 서비스를 사용합니다. 서비스 응답 전에는 해제를 확정하지 않습니다.
  '정지 확인'은 속도 0 명령 발행 확인이며 물리적 정지의 증명이 아닙니다.
- 일시정지는 임무를 보관하고 정지합니다. 임무 취소는 남은 요청을 보류하고 홈으로 복귀합니다.
  비상정지는 홈 이동도 하지 않고 정지를 유지합니다.
- 웹의 호환용 `--with-motion-mux`도 별도 프로세스로 실행합니다. 영상 처리가
  정지 중재 타이머와 같은 executor를 점유하지 않습니다.

## 섹터 도착 후 ArUco 확인

이전 코드는 경로 완료 후 정지해 마커가 영상에 나타나기만 기다렸습니다.
이제 지정 카메라로 **저속 탐색 → 가로 중앙 정렬 → 정지·연속 영상 확인**을 수행합니다.
ID가 검출됐다는 이유만으로 배송 완료 처리하지 않습니다.

- Nav2의 해당 목표 완료, mux 정지 응답, 실제 odom 정지를 먼저 확인합니다.
- 전진·후진 없이 기본 `0.12 rad/s`로 제한된 범위를 탐색합니다.
  실제 odom 회전량, 최대 45초, 선회 범위를 넘기면 임무를 보관하고 일시정지합니다.
- 목표 ID의 네 모서리가 영상 안에 있고 충분히 크게 검출돼야 정렬합니다.
  영상 가로 중앙에서 ±4% 폭 안에 들어오면 0 명령을 내립니다.
- 위치·라이다·선택 카메라가 신선하고 회전 공간이 확보된 상태에서,
  정지와 0.6초 이상의 안정 상태 및 신규 영상 3장 이상을 확인합니다.
  이어서 임무의 연속 확인 프레임 조건을 통과해야 다음 목표로 이동합니다.
- 조이스틱·비상정지·센서 이상이 우선합니다. 카메라 단절이나 공간 부족 상태에서
  억지로 회전하지 않으며, 확인 실패를 배송 완료로 바꾸지 않습니다.

회전 명령도 기존 mux를 경유합니다. `operation=marker_alignment`, 선속도 0,
위치 신뢰도의 명시적 `autonomous_allowed=true`가 필요합니다.
로봇과 PC 모두 같은 새 소스로 업데이트하고 다음 정상 종료 후 다시 실행해야 합니다.
실행 중인 팀원의 실차 시스템을 이 작업에서 재시작하지 않습니다.

기본값을 바꾸려면 웹 실행 명령 뒤에 다음 인자를 추가할 수 있습니다.

```bash
./scripts/run_classroom_web_16.sh \
  --marker-search-speed 0.10 \
  --marker-center-gain 0.35 \
  --marker-center-tolerance 0.08 \
  --marker-search-timeout 45
```

두 카메라는 보정 후 똑바로 보이는, 좌우가 반사되지 않은 영상을 기준으로
우측 오차에 음의 차체 yaw를 사용합니다. 후방이라는 이유로 부호를 반전하지 않습니다.
반사된 영상일 때만 `--marker-front-yaw-sign 1` 또는 `--marker-rear-yaw-sign 1`로
명시적으로 바꿉니다. 차체 yaw만 제어하므로 영상의 세로 중심은 조절할 수 없습니다.
세로 위치가 너무 높거나 낮으면 카메라 설치 각도·마커 높이를 조정해야 합니다.

## 기록·반복 시험

가제보 `/clock`은 50 Hz, 카메라는 8 Hz로 제한합니다. 카메라 해상도와
로봇 형상은 유지하며 임시 SDF만 바꾸므로 ROBOTIS 원본은 수정하지 않습니다.
`camera_update_rate:=값`으로 영상 갱신률을 바꿀 수 있습니다.
조종기 영상 변환도 최대 8 Hz로 제한하고 주행 중 자동 파라미터 탐색을 줄입니다.

실행 스크립트는 기본 `SMART_VISION_DDS_TRANSPORT=udp`로 Fast DDS 프로필을
적용합니다. 실차는 LAN UDP 프로필, 격리 시뮬레이션은 loopback 프로필을 사용합니다.
Humble의 `ROS_LOCALHOST_ONLY=1` 모드가 추가하는 SHM까지 제거하는 설정은 아닙니다.
사용자가 지정한 DDS 프로필과 다른 RMW는 덮어쓰지 않습니다. 이전 미들웨어 기본 설정으로
시험하려면 실행 명령 앞에 `SMART_VISION_DDS_TRANSPORT=default`를 붙이세요.
`.bashrc`나 OS 공유 메모리는 변경하지 않습니다.

발행 방식 비교는 아직 선택 사항입니다. 기본값은 바꾸지 않으며, 실행 명령 앞에
`SMART_VISION_DDS_PUBLICATION_MODE=ASYNCHRONOUS`를 붙이면 해당 실행 트리에서만
Fast DDS의 비동기 발행을 요청합니다. 비교값은 `SYNCHRONOUS`와 `AUTO`이며
대문자로 입력합니다. 변수가 없거나 빈 값이면 현재 설정을 유지합니다.
이미 지정된 `RMW_FASTRTPS_PUBLICATION_MODE`가 있으면 그 값이 우선하고,
다른 RMW에는 적용하지 않습니다. 이 옵션은 전송 프로필 선택과 별개이므로
`SMART_VISION_DDS_TRANSPORT=default` 또는 사용자 XML과 함께 사용할 수 있습니다.

[Humble 공식 설명](https://github.com/ros2/rmw_fastrtps/blob/humble/README.md#change-publication-mode)에
따르면 미지정 기본값은 동기 발행이며, 발행 중 대기가 사용자 실행 스레드를 막을 수 있습니다.
비동기 방식은 발행을 배경 스레드로 넘기지만 큐 적체나 지연 해결을 보장하지 않습니다.
`RMW_FASTRTPS_USE_QOS_FROM_XML=1`이면 XML의 발행 정책이 위 환경변수보다 우선합니다.
비교 시험에서는 정지 상태에서 실행 트리를 다시 시작하고 발행 호출 시간·제어 수신 지연·
정지 응답을 함께 비교합니다. 시각·명령 만료·안전정지 기준은 그대로 유지합니다.

오류 발생 시 기본 30초 전/5초 후 센서·목표·경로·제어 상태를
`~/.ros/smart_vision_amr/incidents`에 gzip JSONL+manifest로 저장합니다.
영상·인증 정보는 수집하지 않습니다. rosbag 형식은 아닙니다.

```bash
# ROS 환경과 도메인을 실행 중인 시스템에 맞춘 뒤 수동 기록
ros2 service call /smart_vision_amr/capture_incident std_srvs/srv/Trigger '{}'
```

[동일 경로 반복 시험](NAVIGATION_BENCHMARK.md)은 도착 여부·시간·경로 오차·재계획·
속도 변화량을 CSV/JSON으로 남깁니다. 파일 설정 해시를 함께 기록하므로 튜닝 전후를 구분할 수 있습니다.

조종기에서 YAML 기본값 저장 시 원본 백업과 `.parameter-history` 이력을 함께 남깁니다.

```bash
cd ~/Team2_workspace/src/SMART-VISION-AMR
# 저장 이력 확인
python3 scripts/parameter_history.py ros2_ws/src/smart_vision_amr/config
# 출력된 이력 파일 중 하나를 선택해 복원
python3 scripts/parameter_history.py /절대경로/.parameter-history/선택한파일.json --restore
```

이후 편집된 파일이나 변조된 백업은 덮어쓰지 않습니다. 복원은 YAML만 변경하며,
현재 실행 중인 ROS 파라미터는 별도로 적용하거나 해당 노드를 재시작해야 합니다.
