올라갑니다. 작은 전진 헤딩 보정 때문에 선속도를 매번 0으로 만들지 않습니다.

경로가 갑자기 바뀌거나 충돌 위험이 생기면 이 완만한 변화보다 즉시 감속·정지를 우선합니다.

[DWB 원인 분석](CONTROLLER_INCIDENT_REPLAY_20261104.md)에 정리했습니다.

동일 costmap·TF·경로에서 정상 전진이 왜 불리하게 채점됐는지 설명합니다.

## 과거 20cm 모델의 재현 증거

기록된 scan·odom·TF·경로를 실제 Humble DWB에 넣은 시험에서 기존 DWB는
`v=0, w=-0.2727rad/s`, 수정 DWB는 `v=0.1042m/s, w=-0.0897rad/s`를 선택했습니다.
차체 반경은 양쪽 20cm입니다. **17cm 설정 하나가 직접 원인은 아니었습니다.**
당시 costmap 전체는 기록에 없어 scan으로 다시 구성했습니다. 이 고정 입력 시험은
원인을 좁히는 증거이며, 폐루프 완주를 대신하지 않습니다.

동일 Home에서 수행한 Gazebo 접근 비교는 다음과 같습니다. 양쪽 모두 실제 방식의
웹 초기 위치 지정·정지 확인·비상정지 해제·pre-arm 후 출발했습니다.
충돌 모델 반경·Nav2 팽창은 20cm, A* 팽창은 4셀이었던 시험입니다.
원자료는 [접근 비교 기록](../benchmarks/navigation_validation_20261104/approach_comparison.json)에 있습니다.

| 재고 요청→초기 위치·pre-arm→적재 확인→Sector 3 중 장애물→Home | 통과 | 실제 기존 경로를 막는 상자, 우회 주행, 상자 4회 이동·제거, 관측 표시 해제, Home 정지 확인 |
| Sector 1→2→3→Home | 당시 기록 미확정 | 종결 판정이 기재되지 않은 기록을 합격으로 바꾸지 않음 |
| Sector 1→2→Home 중 짧은 센서 지연 | 당시 기록 미확정 | 종결 판정이 기재되지 않은 기록을 합격으로 바꾸지 않음 |
| 당시 Python 회귀 / C++ / PC 빌드 | 통과 | 당시 Python 2,265건, C++ 9건, 두 ROS 패키지 빌드. 이후 변경의 최종 검사 수치와 구분 |

장애물 시험은 **기존 경로를 실제로 막는 상자**인지도 검사합니다. 초기 시험에서
상자가 경로를 막지 않아 우회 검증에 실패했고, 시험용 actor의 고정 24cm 계산을
20cm/4셀 설정과 정확한 사각 상자 거리 계산으로 고쳤습니다. 가짜 통과로 기록하지 않습니다.

그 뒤 폐루프 시험에서는 상자에 2cm보다 가까워져 실패한 경우도 보존했습니다.
중심 셀·차체 외곽 검사를 분리해 재생했고, 외곽 검사가 충돌 후보 2개를 추가로 거부하면서
유효 전진 후보 269개를 유지하는 것을 확인했습니다. 이후 20cm 모델의 통과 시험에서는 상자가
원래 경로를 2.68cm 침범했고, 변경 경로를 만든 뒤 실제 차체가 최소 **3.11cm** 간격으로
통과했습니다. 이 수치는 현재 22cm 모델의 여유가 아닙니다.
실제 위치 기준 2cm 검사와 25cm 도착 검사는 완화하지 않았습니다.

후속 시험에서도 실패·중단이 있었습니다. 국소 경로 변경이 추종기에 전달되지 않은
문제, 측면 반사와 실제 경로 장애물의 혼동, LiDAR guard 정지를 추종기 실패로 누적한
문제를 수정했습니다. 과거 통과 기록이 이 후속 실패를 상쇄하지는 않으며, 수정 후
같은 전체 절차를 다시 통과해야 합니다.

## 22cm 모델의 변경 이력 — 아래 팽창 비교는 진입 정렬 수정 전

현재 정적 지도 기준은 **반경 22cm**, **A* 사각 팽창 5셀**, **45cm 중앙 선호 비용**,
`ObstacleFootprint.scale=0.02`, footprint padding 0입니다.
5셀은 축 방향으로 최소 25cm의 셀 간격을 확보하고 대각선에서는 더 보수적입니다.
45cm는 경로 선택 선호이며 통행 금지 반경이 아닙니다. Nav2 팽창도 차체 반경에
더하는 추가 길이가 아니라 비용 영역의 총 반경입니다.

| Nav2 비용 팽창 후보 | 고정 차체 / A* | 정렬 수정 전 장애물 시험 결과 |
| --- | --- | --- |
| 0.22m — 현재 YAML | 0.22m / 5셀 | Home 완료, 제거 전 우회 실패 |
| 0.30m | 0.22m / 5셀 | 상자 4회 이동·Home 완료, 제거 전 우회 실패 |
| 0.40m | 0.22m / 5셀 | 적응형 장면 우회 실패 / 후속 고정 장면 입력 무효 |

[고정 장면 비교표](../benchmarks/driving_parameter_tuning_20261104/FIXED_SCENE.md)에는
공통 소스에서 바꾼 값과 입력 무효를 따로 기록했습니다. 모든 경우를 합격으로 표시하지 않습니다.
특히 상자 제거 후 Home 도착은 상자를 남긴 상태에서의 우회 성공과 구분합니다.

비교할 때 재고 요청→초기 위치→정지 확인→비상정지 해제→pre-arm→적재 확인→출발,
후방 표식 확인·5초 대기·Home 복귀까지 같은 절차를 사용합니다. 장애물 설치가 원래
경로를 실제로 막는지, 국소 경로가 추종기에 전달됐는지, 실제 차체 간격과 최종 정지가
합격 기준을 만족하는지를 함께 기록합니다. 최종값 선택 전에는 전체 시험 완료로 표시하지 않습니다.

주행 중 장애물 복구 우선순위는 **국소 우회 → 검증된 짧은 후진 → 전체 재계획**입니다.
새 목적지를 처음 지정할 때는 정상 A*로 시작합니다. 후진은 이전 액션의 취소 종결과
실제 정지, 후방 궤적·공간을 확인한 뒤 실행하며, 끝나면 같은 목표를 새로 계획합니다.
후진 근거가 없으면 정지 위치에서 전체 재계획으로 넘어갑니다.

국소 우회는 전체 재계획보다 우선하며 진행 중 우회의 새 실제 방해도 남은 3회 예산에서
복구합니다. 실패 액션 뒤에는 **종결 확인과 시도 구간의 실제 차체 교차 근거**가 있어야
국소 복구를 먼저 합니다. 새로운 관측이나 단순 재계획만으로 예산을 리셋하지 않고,
지도 자세와 독립 odometry로 원래 경로에 재합류한 사실을 확인합니다.

LiDAR guard 정지는 장애물 없는 추종기 정체와 구분합니다. guard로 차단된 실행을
실패 기억·추종기 3회 예산에 넣지 않습니다. 실제 장애물 처리는 별도의 raw·관측·기억
근거를 그대로 사용하며, 센서·TF·취소 종결 검사를 생략하지 않습니다.

스캔 보정은 **원본 시각·수신 경과 1초 미만 / 최신 odom 자세 250ms 미만**에서
동작합니다. 스캔 획득 당시 자세와 최신 자세의 차이로 반사점을 재투영하고, 최신 자세
이후의 잔여 지연만 최대 속도에 따른 방향별 이동 상한으로 검사합니다. 새 스캔이 TF보다
조금 앞서면 `pending`으로 보관하며, 이전 검증 스캔이 유효한 동안 이를 계속 보정해
사용합니다. 새 raw 반사가 현재 차체·요청 궤적에 교차하면 첫 관측부터 정지하고,
TF 오류·invalid·stale 입력에서는 정지를 유지합니다.

| guard 입력 회귀 | 결과 | 범위 |
| --- | --- | --- |
| 실제 tf2 Buffer: TF 20Hz·scan 10Hz, scan 시각이 10ms 앞섬 | 통과 | 보간 대기 중 이전 검증 스캔을 보정하며 불필요한 0속도 펄스 방지 |
| 200ms 지연·전방 장애물 접근 | 통과 | 이동 후 차체/궤적 교차를 반영해 정지 |
| 200ms 지연·평행 측면 벽 | 통과 | 원형 차체와 실제 교차가 없는 평행 주행 허용 |

위 회귀는 시간·기하 입력에 대한 판정입니다. 전체 Python·빌드의 최종 검사는 별도로
기록합니다. **위 팽창 비교는 진입 정렬 수정 전의 실패 또는 입력 무효 기록**이며,
이후 22cm 기본값의 통과 결과는 아래에 따로 구분합니다. 과거 실패를 소급해 합격으로 바꾸지 않습니다.

Gazebo의 실제 위치를 사용한 합격 검사와, 웹의 추정 위치·완료 표시는 따로 확인합니다.
Pi 부하·Wi-Fi 전송·OpenCR 통신·배터리 전압강하·실제 바닥 미끄러짐까지 동일한 시험은
아니므로, 다음 실차 시험에서 같은 경로·속도·후진 조건을 반복 확인해야 합니다.

### 복구 정책 교체 후 첫 시험

[첫 실행 원자료 요약](../benchmarks/driving_parameter_tuning_20261104/replaced_policy_first_trial.json)은
재고 요청부터 pre-arm·주행을 포함한 같은 고정 상자 장면입니다. **진단 중단·실패**로
기록했으며 Sector 3·Home 도착과 표식 확인을 완료하지 못했습니다.

| 확인 항목 | 결과 |
|---|---|
| 실제 pre-arm | 통과 |
| 전체 계획 / 국소 시도 | 5회 / 3회 |
| 실제 후진 | 0회; 당시 선택기는 이력 부족·궤적 조건으로 거부 |
| 상자 이동 | 3/4회; 네 번째는 실제 이동 여유 검사에서 보류 |
| 실제 최소 상자 여유 | 5.03cm |
| raw-scan guard 정지 표본 | 0초; 장시간 정지의 직접 원인은 guard가 아니었음 |
| 상자 제거 후 재개 | 실패; 기억 해제 메시지와 복구 대기 의존성 분석으로 연결 |

실제 odom은 이동 이력을 보유했지만 지도 자세 기반 이력은 위치 보정의 영향을 받았습니다.
또한 당시 주행 곡선의 방향 차이가 있어 이력을 보존하는 수정만으로 후진 성공을 주장할 수 없습니다.
수정 후 [실제 odom 입력 A/B](../benchmarks/driving_parameter_tuning_20261104/odom_trail_recovery/README.md)에서는
같은 기록의 보수적인 실제 기억 15셀 상태를 양쪽 모두 거부했고, 생산자가 확인한 기억 0셀
상태에서는 새 방식만 11.748cm 후보를 선택했습니다. 실제 후진 축의 전체 차체 궤적과
최근 이동 통로를 함께 확인한 오프라인 결과이며, 실제 폐루프 수행 성공과는 구분합니다.
제거 후 실패는 [기억·출발점 감사](../benchmarks/driving_parameter_tuning_20261104/start_egress_audit/README.md)에
원본 수신 시각과 원자적 snapshot의 한계를 구분해 정리했습니다.

실행 중 소스 변경 없이 정식 실차 YAML 값과 같은 상자 좌표를 사용했습니다.

| 로컬 지도 해상도 | Sector 3·Home | 후진 요청 | 상자 이동 | 제거 전 우회 | 전체 |
|---|---|---:|---:|---|---|

정식 YAML은 그대로입니다. 추가 비교에서는 후진 선택기의 실제 첫 거부 조건을 분리해야 합니다.

### 큰 우회 진입각을 무시한 추종 정책

[수락 경로 추종 감사](../benchmarks/driving_parameter_tuning_20261104/accepted_route_tracking_20261105/README.md)는
실제 FollowPath ACK의 `path_stamp`와 일치하는 구간만 대조합니다. 최초 목적지 방향 정렬이
완료되면 같은 목표의 큰 우회 변경도 다시 정렬하지 않던 정책을 확인했습니다.

| 기록 | 새 우회 진입각 오차 | 실제 최대 경로 횡오차 | TF 합성 추정 횡오차 |
|---|---:|---:|---:|
| v2 기준 | 47.5° | 7.99cm | 7.16cm |
| 로컬 2.5cm 후보 | 75.5° | 14.54cm | 11.20cm |

2.5cm 후보의 한 지점에서 계획선 위 차체의 상자 여유는 18.59cm였지만 실제 차체는
상자 쪽으로 벗어나 여유가 4.06cm로 줄었습니다. 이후 후진의 첫 거부는 실제 원본 격자와
22cm 차체가 겹친다는 판정이었고, 과거 헤딩·거리 증가 휴리스틱까지 진행하지 않았습니다.
따라서 이 사례를 후진 거리 임계값만 낮춰 해결했다고 처리하지 않습니다.

이를 **크게 바뀐 가까운 우회 경로에 진입하기 전 정지·방향 정렬**로 수정했습니다.
기존 FollowPath의 실제 취소 종결 후, source 시각과 수신 시각 모두에서 0.2초 이상
연속 정지를 확인하고 기존 센서·제어권·Nav2 회전 충돌 검사를 거쳐 Spin을 시작합니다.
같은 경로 재발행·연속 나머지 경로·먼 구간만의 변경은 반복 선회하지 않습니다.
우회 정렬은 경로당 2회·같은 명시 목표에서 총 6회로 제한하며, 소진 시 목표를 보존하고
운용자 재개를 기다립니다. 선회 중 새 경로가 도착해도 이전 액션 종결과 새 정지 확인을 생략하지 않습니다.

### 진입 정렬 수정 후 — 같은 고정 장면 첫 통과

[전후 비교](../benchmarks/driving_parameter_tuning_20261104/recovery_replacement_validation/material_heading_comparison.json)와
[독립 감사](../benchmarks/driving_parameter_tuning_20261104/recovery_replacement_validation/independent_material_heading_audit.json)는
같은 상자 좌표에서 **follower만 변경한** 시험입니다. 정식 22cm 차체·Nav2 비용 팽창,

## 다른 PC에서 같은 가상 시험 실행

[Gazebo 설치](GAZEBO.md)를 완료한 PC에서 아래 한 터미널만 실행합니다.
이 명령은 가상 로봇·주행·웹·시험을 함께 시작하고 종료 시 자신이 실행한 프로세스를 정리합니다.

```bash
cd ~/Team2_workspace/src/SMART-VISION-AMR
git pull --ff-only &&
./scripts/setup_pc_runtime.sh --no-install &&
python3 scripts/run_classroom_staged_validation.py \
  --run 03_web_sector3_clean,25_web_inventory_sector3_moving_obstacle,12_web_integrated_clean,16_web_transient_resume \
  --physical-footprint --memory-session \
  --nav-params-source ros2_ws/src/smart_vision_amr/config/classroom_demo_operator_20261104.yaml \
  --leg-timeout 240 --obstacle-hold-timeout 0 \
  --output "/tmp/classroom-validation-$(date +%Y%m%d-%H%M%S)"
```

실행 중 관제는 <http://127.0.0.1:8792/>입니다. 같은 Wi-Fi의 다른 기기는
`hostname -I`로 확인한 **시험 PC의 IP**를 사용합니다. 로봇 IP가 아닙니다.
시험기가 웹 임무를 조작하므로 관제 화면에서 별도 주행 명령을 겹쳐 보내지 않습니다.
실차는 domain **16**, 웹 **8790**이며 [팀원용 터미널별 실행·웹 운용 순서](TEAM_QUICKSTART.md)를 따릅니다.
새 DWB 플러그인이 있으므로 PC 재빌드가 필요하며, 로봇 코드도 업데이트·재빌드한 뒤 실행합니다.
위 명령은 현재 YAML을 사용하는 재시험 명령입니다. 고정 장면 1회 통과와 별개로
전체 경로·반복·지연 시험 및 실차 검증의 합격을 보장하지 않습니다.
