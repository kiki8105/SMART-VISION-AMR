# 재고 부족 요청과 로봇 배송

## 화면과 사용자

| 사용자 | 주소 | 기능 |
| --- | --- | --- |
| 0 · 로봇 운용자 | `http://PC_IP:8790/` | 부족 요청 확인, 적재 확인과 출발, 일시정지, 홈 복귀, 비상정지 |
| 1~99 · 재고 관리자 | `http://PC_IP:8790/inventory` | 부족한 위치·물품·수량·메모 송출, 자신의 요청 상태 확인, 배차 전 요청 취소 |

두 화면은 같은 PC에서 실행하는 서버를 사용합니다. 휴대폰이나 다른 PC에는
ROS를 설치하지 않고 같은 네트워크에서 접속합니다. 관리자 번호와 목적지의
ArUco ID는 서로 다른 값입니다. 예를 들어 사용자 12가 ArUco 2 위치의 부족을
요청할 수 있습니다. 위치는 현재 지도에 등록된 마커 좌표를 사용합니다.

서버 PC의 `http://localhost:8790/`은 자동으로 운용자 화면에 연결됩니다.
강의실 실차용 `web_16`은 다른 기기에서도 **ROS Domain ID 16**으로 연결합니다.
재고 관리자는 사용자 번호 1~99와 Domain ID 16을 입력합니다. 매번 터미널에서
코드를 확인할 필요가 없습니다. Domain ID는 비밀번호가 아니므로 같은 네트워크에서
16을 아는 사람은 운용자 화면에도 접속할 수 있습니다. 접속 후 역할별 API는 분리하며,
도메인이 변경되면 이전 도메인에서 발급한 세션은 더 이상 사용할 수 없습니다.
일반 시뮬레이션 실행 스크립트는 기존 코드 방식이 기본이며 `--access-mode code`로
운용자·관리자 별도 코드 방식을 선택할 수 있습니다. 서버 PC의 **차량 연결** 창에서
현재 도메인과 접속 주소를 확인할 수 있습니다.
관리자용 세션은 로봇 출발·속도·카메라 API를 사용할 수 없습니다.
관리자 번호는 실습용 선택 식별자이며 개별 비밀번호 계정은 아닙니다.

## 차량 전원 신호와 전압

운용자·재고 관리자 화면의 상단 배지는 `/battery_state`의
`sensor_msgs/msg/BatteryState.voltage`를 V 단위로 표시합니다. 재고 관리자 화면은
로그인 후 표시하며 전압 정보만 추가로 읽을 수 있고 주행 API 권한은 그대로입니다.
웹을 새로 열거나 새로고침하면 적용됩니다.

- **전원 신호 수신**: 최근 5초 안에 유효한 양수 전압을 수신했습니다.
- **전원 신호 대기**: 현재 연결에서 받은 전압 데이터가 없습니다.
- **전원 신호 지연**: 5초 이상 갱신되지 않았습니다. 마지막 전압은 `이전값`으로 표시합니다.
- **전압 확인 필요**: 최근 메시지의 전압이 0·음수·NaN 등 유효하지 않습니다.
- **웹 연결 확인**: 브라우저가 웹 서버에 연결하지 못해 현재 상태를 확인할 수 없습니다.

토픽 이름과 마지막 수신 시간은 배지에 마우스를 올리거나 키보드로 포커스해 확인합니다.
배지는 전압 토픽의 수신 상태이며 전원 차단과 네트워크 단절을 구분해 단정하지 않습니다.
배터리 잔량을 전압에서 임의 추정하지 않으며, 이 표시가 주행을 자동 시작하거나 중지하지 않습니다.
전압 메시지도 원본 시각이 5초 이내여야 하므로 PC와 로봇의 시각이 맞아야 합니다.

기본 TurtleBot3 브링업이 이 토픽을 발행하며 별도 전압 발행 노드는 필요하지 않습니다.
다른 이름을 사용하는 로봇은 웹 서버 옵션 `--battery-topic /robot_name/battery_state`로
같은 메시지 타입의 토픽을 지정할 수 있습니다. 토픽 변경 후에는 웹 서비스를 재시작합니다.

## 웹 조이스틱과 임무 중 개입

운용자 화면에만 수동 우선 조이스틱이 있습니다. 휴대폰에서는 누른 채 드래그하고,
PC에서는 마우스로 드래그하거나 조이스틱에 초점을 둔 뒤 화살표 키를 누릅니다.
전후진 최대 0.12m/s, 회전 최대 0.60rad/s이며 놓기·키 해제·화면 전환·연결 끊김은
수동 명령을 종료합니다. 재고 관리자 화면에는 조종 기능이 없습니다.

임무 중 누르면 현재 경로 추종 동작의 실제 취소 완료와 속도 출력 차단을 확인한 뒤
수동으로 전환합니다. 임무 목표·방문 순서·현재 순번·방문 완료 내역·고정 홈과 배송 큐는
유지됩니다. 조작 중에도 새 배송 요청을 뒤에 추가할 수 있습니다.
놓으면 수동 속도를 0으로 만들고 같은 목표를 새 시각으로 다시 전달합니다.
현재 위치에서 기존 목표로 경로를 재계획하므로 수동 이동 전의 경로선과는 달라질 수 있습니다.
새 목표에 대한 주행 시작 응답 이후에만 자동 속도를 통과시킵니다.
조작 전에 이미 일시정지된 임무는 자동으로 재개하지 않습니다.

우선순위는 **비상정지 > 수동 조종 > 자동 주행**입니다. 조이스틱 입력은 10Hz로
전달되며 0.5초 동안 갱신되지 않으면 수동 속도를 0으로 만들고 기존 임무 재개 절차를
시작합니다. 이때 위치·LiDAR·오도메트리·카메라 등 임무 조건이 복구되지 않았으면
목표를 보존하고 정지 상태로 기다립니다. 명시적 일시정지·홈 복귀·비상정지 명령은
조이스틱의 자동 재개보다 우선합니다. 늦은 요청과 다른 운용자의 동시 개입은
세션·순서 번호로 차단합니다.

Nav2 속도는 `/smart_vision_amr/navigation_cmd_vel`에서 `command_stamper`가 시각·순서를 붙여
`/smart_vision_amr/navigation_control`로 전달합니다. 웹 수동 제어는
`/smart_vision_amr/manual_control`로 분리하며 `motion_mux`만 최종 `/cmd_vel`을
출력합니다. 강의실 기본 구성은 로봇 runtime이 mux를 소유하므로 브링업과 LiDAR·오도메트리가 준비되면
명시적으로 비상정지를 해제한 뒤 위치 추정이나 A* 없이도 수동으로 조종할 수 있습니다. 자동 임무에는 기존 주행 구성이
계속 필요합니다. 일반 시뮬레이션·하드웨어 런치는 기본적으로 mux를 함께 실행하고,
`scripts/run_classroom_navigation_16.sh`와 웹은 로봇 runtime의 mux를 사용하며 중복 생성하지 않습니다.

업데이트 전 실행한 Nav2나 기존 Qt 조종기가 `/cmd_vel`에 직접 발행 중이면 새 mux는
정지 명령도 끼워 넣지 않고 출력을 보류하며 UI에 충돌 사유를 표시합니다.
이전 주행 터미널을 Ctrl+C로 종료한 뒤 `scripts/run_classroom_navigation_16.sh`를 다시 실행하고,
기존 Qt 조종기는 종료한 상태에서 웹을 사용합니다. 부팅 시 웹은 임무를 자동 출발시키지 않습니다.

## 실차 16 · 강의실 홈과 Sector 구성

실차용 웹은 `/home/kiki/turtlebot3/scripts/web_16`으로 실행합니다. Gazebo를 실행하지 않고
실제 시간을 사용합니다. 정리한 지도를 패키지의 `maps/classroom_20261027_cleaned.yaml`과
같은 이름의 PGM으로 보관했으며 웹·주행 스크립트가 동일한 파일을 사용합니다.
회색 205가 실제 Nav2에서도 미확인으로 남도록 편집본의 `free_thresh`를 0.196으로
설정했습니다. 원본 지도는 보존했습니다.

| ID | 명칭 | x (m) | y (m) | 관측 카메라와 벽 | 차체 전방 yaw (rad) |
| --- | --- | --- | --- | --- | --- |
| 0 | 홈 | -0.11 | -0.79 | 후방 · 중앙 사각 장애물 반대편 왼쪽 벽 | 0 |
| 1 | Sector 1 | 1.60 | 0.08 | 전방 · 오른쪽 벽 | 0 |
| 2 | Sector 2 | 1.71 | -3.31 | 전방 · 아래쪽 벽 | -1.570796 |
| 3 | Sector 3 | -0.105 | -2.55 | 전방 · 작은 방의 위쪽 벽 | 1.570796 |

Sector 3은 지도 왼쪽 아래의 가벽으로 구분된 방 내부에서 추출했습니다.
실차에서 3번 마커가 카메라 시야 밖에 있어 관측 지점을 위쪽 벽에서 0.20 m 떨어뜨렸습니다.
3번은 일반 방문 구역이며 고정된 종료 지점이 아닙니다. 배송은 접수 순서를 따르고
모든 요청을 처리한 뒤 0번 홈으로 복귀합니다. 기본 수동 실습 순서는 1→2→3입니다.
명칭과 관측 좌표는 `config/aruco_classroom_markers.yaml`에서 수정합니다.
`yaw`는 차체 전방(`base_footprint`) 방향입니다. 홈 0번은 후방 카메라로 보므로
카메라가 `yaw + π` 방향을 봅니다. Sector 1~3은 전방 카메라로 보며 카메라가
`yaw` 방향을 봅니다. 각 목표의 카메라 선택은
`config/aruco_classroom_markers.yaml`의 `camera` 필드에 등록합니다.
위 좌표는 벽에 붙는 마커 좌표가 아니라 로봇이 멈춰 관측할 위치입니다.
지도 핀의 화살표는 차체 전방이며 홈 후방 카메라만 반대쪽을 봅니다. 실제 부착 후
각 목표의 해당 카메라 영상에 마커가 들어오는지 확인합니다.
마커를 옮기면 이 파일의 yaw와 관측 위치를 함께 확인하고, 홈 방향을 변경할 때는
웹에 저장된 Homepoint의 yaw도 맞춥니다.

재시작 후 AMCL의 지도상 초기 위치는 별도로 지정해야 합니다. 로봇이 실제로
홈 `(-0.11, -0.79)`에 정지하고 후방 카메라가 0번 마커를 보는 경우에만 PC에서
`scripts/set_classroom_home_pose_16.sh`를 실행합니다. 이 명령은 차체 전방
방향을 `yaw=0`으로 설정하며 로봇을 움직이지 않습니다. 먼저 실차 Bringup과
PC의 강의실 Navigation을 실행해야 합니다.
운용 웹의 **자세 초기화**는 등록된 홈을 초기 추정값으로 넣은 뒤, 라이다와 지도를
대조하며 저속 제자리 회전을 수행하는 별도 방법입니다. 최신 `/scan`·`/odom`과
회전 여유, AMCL을 확인하며 조이스틱 개입 시 멈춥니다. 위치 추정이 완료돼도
배송 임무가 자동으로 출발하지 않습니다. 홈에서 시작하지 않았다면 이 버튼의

허용하지 않습니다. 실제 `/map`의 셀·원점·해상도가 설정 지도와 일치하고 최신 위치·센서·
카메라 및 주행 노드가 준비돼야 합니다. 다른 지도 수신 시 진행 중 운행을 일시정지합니다.
강의실 웹 지도는 `config/classroom_floorplan.yaml`에 별도로 작성한 직선 평면도를
기본 표시하며 **평면도 / 원본** 전환을 지원합니다. 외벽·내부 가벽을 수직·수평의
8cm 두께로 통일하고 중앙 장애물을 직사각형으로 표현했습니다. 상단 돌출·잔선은
표시에서 제거했고 작은 방의 출입구와 외곽 입구는 보존했습니다.
이 표시 전용 도면에 홈·Sector 이름표를 같은 실제 좌표의 핀으로 연결합니다.
도면의 자동 맞춤·경로·로봇 위치·거리 눈금은 같은 좌표 변환을 사용하며 실제 지도 데이터는
이 표시 기능으로 수정하지 않습니다. 다른 `/map`이 들어오면 설정 지도의 미리보기를 유지하고
다른 좌표계의 차량·경로를 표시하지 않습니다.

강의실 전용 A*는 `config/classroom_hardware_nodes.yaml`을 사용합니다.
Sector 1 좌표를 유지하면서 경로가 생기도록 장애물 팽창을 5셀(0.25m)로 지정했고,
미확인 영역을 차단한 상태로 네 지점 간 모든 경로 및 차체 반지름 0.22m+여유 0.02m를
검사했습니다. 실제 주행 검증을 대신하는 검사는 아닙니다.
설정과 요청 이력은 `~/.config/smart-vision-amr/classroom-16.json` 및 같은 폴더의
`classroom-16.inventory-domain-16.json`에 저장하며 다른 지도·도메인의 이력을 가져오지 않습니다.

웹사이트의 부팅 시 자동 실행·백그라운드 실행은 [상시 실행 안내](classroom_web_service.md)를
따릅니다. 이 PC에는 `smart-vision-classroom-web.service` 사용자 서비스를 등록해 웹만
자동으로 실행합니다. 서비스를 쓰는 동안 같은 포트의 `web_16`을 추가 실행하지 않습니다.
브링업·카메라·위치 추정·주행은 별도 실행하며 웹 시작만으로 임무가 출발하지 않습니다.

## 로봇 Bringup과 카메라를 함께 실행

새 기본 구성은 로봇 내부에서 독립 바퀴·IMU EKF·안전 감시·최종 속도 중재기를 함께 실행합니다.
처음에는 [실차 설치·실행 안내](hardware_ekf.md)를 따라 로봇에 저장소를 클론하고
`./scripts/setup_robot_runtime.sh`를 실행합니다. 셸 파일만 복사해서는 설치되지 않습니다.

로봇 SSH 터미널에서 기존 Bringup·카메라를 Ctrl+C로 종료한 뒤 실행합니다.

```bash
cd ~/SMART-VISION-AMR
ENABLE_FRONT_CAMERA=true ./scripts/robot_bringup_camera_16.sh
```

기본 워크스페이스는 `~/turtlebot3_ws`, 도메인은 16, 모델은 waffle_pi,
`LDS_MODEL` 기본값은 LDS-03입니다. 실제 라이다 모델과 일치하는지 확인합니다.
후방 웹캠은 재부팅 후에도 유지되는 `/dev/v4l/by-id/...-video-index0` 경로를
사용합니다. 웹캠을 교체했다면 `CAMERA_DEVICE`로 새 경로를 지정합니다.
기본 카메라 백엔드는 통신량을 줄인 5 FPS JPEG이며
`/camera/image_raw/compressed`를 발행합니다. 원본 영상 토픽도 필요한 경우
`CAMERA_BACKEND=v4l2 ./scripts/robot_bringup_camera_16.sh`로 실행합니다.
스크립트의 기본 전방 설정은 꺼짐이지만 위 명령은 강의실 Sector 마커 확인을 위해 활성화합니다. 실제 전방 영상과
ArUco 검출을 다시 확인해야 합니다. 웹 서비스는 거꾸로 장착된 후방 카메라를
ArUco 검출과 표시 전에 180° 회전합니다.

`v4l2` 백엔드가 필요하지만 `v4l2_camera`가 없다면 로봇에서
`sudo apt install ros-humble-v4l2-camera`로 설치합니다.
전방 카메라 지원 형식 확인에는 `v4l2-ctl`이 필요하며, 없으면
`sudo apt install v4l-utils`로 설치합니다.
시작 전 장치 점유를 확인하며 기존 프로세스를 강제 종료하지 않습니다.
Ctrl+C 또는 필수 Bringup·후방 카메라 프로세스의 종료 시 이 파일이 시작한
프로세스를 모두 정리합니다. 전방 카메라만 종료되면 후방·Bringup은 유지합니다.
전방 카메라 영상과 전방 ArUco 배송 확인은 실차에서 검증해야 합니다. PC에서는
`./scripts/run_classroom_navigation_16.sh`를 함께 실행해야 하며, EKF 센서 점검 후
웹의 비상정지 해제·임무 시작을 별도로 진행합니다. 기존 방식으로 돌아가는
명령과 주의사항은 [실차 EKF 안내](hardware_ekf.md)를 참고합니다.

## Homepoint와 출발

기본 Homepoint는 현재 등록된 마커 0번의 로봇 관측 위치입니다. 미로 지도에서는
약 `x=-3.00, y=-2.00, yaw=0.00`입니다. 다른 위치를 대기 장소로 사용하려면
로봇을 그 위치와 방향에 정지시킨 뒤 운용자 화면에서
**현재 위치를 Homepoint로 설정**합니다. 위치와 방향을 도메인별로 영구 저장하며
새 배송이 시작되거나 도중에 요청이 추가되어도 변경하지 않습니다.

배송은 Homepoint 부근에서 정지하고 최신 위치·센서·카메라 및 주행 노드가
준비된 경우에만 출발합니다. 허용오차는 위치 0.30m, 방향 0.35rad입니다.
Sector 1~3 배송에는 전방 카메라 영상이 출발 조건입니다. 운행 중 영상이
끊기면 목표 경로는 유지하고, 도착 후 마커 확인 단계에서 영상 복구를 기다립니다.
대기 요청이 도착하는 것만으로 출발하지 않습니다. 운용자가 물품을 적재한 뒤
체크박스를 확인하고 **적재 완료 · 출발**을 눌러야 합니다.

## 주행 중 요청과 완료

1. 관리자가 부족 요청을 보냅니다. 서버가 번호를 발급해 영구 저장합니다.
2. 운용자의 적재 확인 후 접수 순서대로 목표를 생성합니다.
3. 주행 중 추가 요청은 현재 목표를 유지하면서 뒤에 연결합니다.
4. 목표 도착과 실제 카메라의 해당 ArUco 확인 후 그 요청을 배송 완료로 기록합니다.
5. 모든 요청을 처리하면 저장한 Homepoint로 자동 복귀해 다음 적재를 기다립니다.

같은 목적지에 대한 서로 다른 요청도 별개 요청으로 기록됩니다. 마지막 배송 후
자동 복귀 중에 요청이 추가되면 홈 목표의 취소를 확인하고 추가 목적지로 이동한 뒤
다시 복귀합니다. 일시정지 상태에서는 요청을 추가해도 자동으로 재출발하지 않고
운용자의 **배송 재개**를 기다립니다. 한 운행은 최대 100개의 방문 목표를 처리하고,
그 이상은 다음 적재 때 처리할 접수 상태로 남습니다.

적재는 운용자의 수동 확인을 사용합니다. 배송 완료는 실제 목표 도착과 마커
확인에 대한 기록이며 물품 하역 자체의 센서 확인은 아닙니다.

## 중지와 복구

- **일시정지**: 현재 위치에서 정지하고 기존 운행을 유지합니다.
- **임무 취소 · 복귀 / 홈 복귀**: 미완료 요청은 접수 상태로 되돌리고 홈으로 복귀합니다.
  새 요청은 다음 적재를 기다리며 사용자가 요청한 복귀를 중단하지 않습니다.
- **비상정지**: 즉시 정지합니다. 해제 후에도 자동 출발하지 않습니다.
- **재시작**: 접수 요청과 완료 이력은 보존하며, 중단된 배송은 접수 상태로 복구합니다.
  로봇을 자동으로 움직이지 않고 Homepoint 복귀 및 운용자의 적재 확인을 기다립니다.

재고 관리자 화면의 **전체 배송 기록 초기화 · 홈 복귀**는 모든 관리자의 완료·취소
기록을 삭제하고, 로봇이 홈 밖에 있으면 기존 홈 복귀 경로를 요청합니다. 이미 홈이고
위치·센서가 최신이면 `이미 홈포인트입니다.`를 표시하며 새 이동 목표를 보내지 않습니다.
현재 운행에 연결된 완료 기록은 그 운행이 홈 도착을 확인한 뒤 자동 삭제합니다.
이 예약은 웹 서버가 재시작되어도 유지되고, 버튼을 누른 이후 새로 생긴 기록은
삭제하지 않습니다. 미완료 요청은 보존하며 복귀 시 다시 접수 대기로 돌립니다.
로봇 연결·위치 확인이 불가능하면 기록 처리 결과와 홈 복귀 불가 상태를 따로 표시합니다.

요청 상태는 `접수 → 대기/운송 중 → 배송 완료`입니다. 관리자는 본인의 배차 전
접수만 취소할 수 있습니다. 네트워크 응답이 끊겨 같은 전송을 다시 눌러도 같은
중복 방지 ID를 사용해 요청이 두 번 만들어지지 않도록 처리합니다.

지도나 주행 경로가 잠시 사라지면 목표를 유지하고 정지 상태에서 재계획합니다.
취소·홈 복귀·목표 변경은 기존 주행의 취소 응답을 확인한 뒤 다음 목표를 전달합니다.

`static_start=True`는 원본 벽뿐 아니라 정적 지도의 인플레이션 안에 현재 셀이
들어간 경우에도 출력됩니다. 원본은 자유 공간이고 차체와 추가 여유가 확보되면
처음에만 최대 7셀의 짧은 탈출 경로를 생성합니다. 장애물에서의 여유가 줄어드는
방향은 사용하지 않고, 정상 공간 이후에는 기존 A*와 6셀 인플레이션을 유지합니다.
원본 점유·미확인 셀 또는 차체 여유가 부족한 위치에서는 계속 정지합니다.
`curve_tuning_simulation_nodes.yaml`의 `robot_radius`,
`start_egress_clearance_margin`, `start_egress_max_cells`가 이 검사 기준입니다.

## 저장 위치

기본 설정은 `~/.config/smart-vision-amr/web-mission.json`이며 Homepoint도 여기에
도메인별로 저장됩니다. 요청과 배송 이력은 같은 폴더의
`web-mission.inventory-domain-도메인번호.json`에 원자적으로 저장합니다.
`--config-file`을 지정하면 해당 설정 파일 옆에 요청 저장 파일을 만듭니다.
