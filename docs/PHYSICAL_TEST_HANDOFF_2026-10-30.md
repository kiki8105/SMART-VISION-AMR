# 2026-10-30 실차 시험 인수인계

**실차 전체 임무 검증은 미통과입니다.** 아래 초기 시험은 구동기 통신 장애로
중단돼 병진 경유점·배송 임무를 실행하지 못했습니다. 이후 후속 시험에서는
Sector 3 표식 확인과 Sector 2 방향 주행까지 확인했으나, 도착 전 구동기가 다시
종료됐습니다. 시뮬레이션 통과 결과와 이 실차 부분 결과를 구분해야 합니다.

| 비교 조건 | 실제 확인 결과 |
|---|---|
| 기본 Fast DDS | 같은 Pi의 안전 메시지가 mux에서 약 1~3.7초 늦게 처리됐습니다. 같은 메시지는 PC 관측기에 즉시 도착한 사례가 있어 PC·로봇 시계 차이만으로 설명되지 않습니다. |
| Fast DDS `ASYNCHRONOUS` | 제어 수신 지연 최대 10.179초가 남았고, 위치 추정 시작 RPC도 완료되지 않았습니다. 해결로 채택하지 않았습니다. |
| 선택 시험 Cyclone DDS | 이번 시험에서 지도·서비스·정지 해제가 진행됐고 일반 위치 확인으로 실제 약 188.8° 회전했습니다. 제어 지연 거부 2회·최대 약 1.28초도 관측돼 통신 문제가 모두 해결됐다고 볼 수 없습니다. |

회전 중 `DynamixelSDKWrapper: no status packet` 오류가 10회 반복된 뒤
`turtlebot3_ros`가 `stack smashing detected`, 종료 코드 `-6`으로 종료됐습니다.

## 재시험 전제

- 충전된 전원과 OpenCR USB·Dynamixel 연결을 확인하고, `no status packet` 반복이나
  드라이버 종료가 없어야 합니다. 전압 수치 하나로 원인을 확정하지 않습니다.
- 원시 바퀴·IMU·배터리 수신을 확인하고, 프로세스 종료 보완 패치를 적용한 실차 재시험을 진행합니다.
- 이전 로봇 브링업과 PC 주행 실행을 종료한 뒤 최신 코드를 양쪽에 적용합니다.
  이번 시험에서 시작한 로봇 실행과 PC 주행 런치는 모두 종료된 것을 확인했습니다.
- 비상정지를 강제로 해제하거나 실제 위치와 다른 Home 초기 위치를 입력하지 않습니다.
  센서·제어권·정지 조건이 모두 통과한 뒤 운용자가 다음 동작을 선택합니다.
- 이번 시험은 제자리 회전만 했으므로 위치를 홈으로 확정하지 않습니다. 충전·점검 뒤
  실제 등록 홈에 놓고 후방 카메라가 0번 마커를 보도록 방향을 다시 맞춥니다.

Cyclone은 이번 비교 시험의 **선택 설정**입니다. PC와 Pi에는 공식 ROS 패키지를 설치했지만,
프로젝트 기본 RMW·QoS·의존성 설치 정책은 바꾸지 않았습니다. 아래 명령은 전제 조건을
충족한 뒤 재시험할 때 사용하며, 세 실행 모두 같은 RMW와 도메인 16을 사용합니다.

## 세 터미널 재시험 절차

**터미널 1 — PC에서 로봇으로 SSH 접속한 뒤 실행**

```bash

RMW_IMPLEMENTATION=rmw_cyclonedds_cpp \
SMART_VISION_TIMING_DIAGNOSTICS=true \
./scripts/robot_bringup_camera_16_ekf.sh
```

원시 센서와 구동기 로그가 정상인지 확인합니다. 후방 카메라는 필수이며 전방 카메라는
기본으로 끕니다. 드라이버 오류가 재발하면 재설정·회전·임무를 진행하지 않고 로그를 보존합니다.

**터미널 2 — SSH가 아닌 로컬 PC에서 실행**

```bash
cd ~/Team2_workspace/src/SMART-VISION-AMR
RMW_IMPLEMENTATION=rmw_cyclonedds_cpp \
./scripts/check_classroom_deployment.sh --live && \
RMW_IMPLEMENTATION=rmw_cyclonedds_cpp \
./scripts/run_classroom_navigation_16.sh
```

점검 실패 시 주행 노드는 시작하지 않습니다. 지도·AMCL·A*·Nav2 준비와 센서 상태를 확인합니다.

**터미널 3 — 로컬 PC에서 웹 실행**

```bash
cd ~/Team2_workspace/src/SMART-VISION-AMR
RMW_IMPLEMENTATION=rmw_cyclonedds_cpp ./scripts/run_classroom_web_16.sh
```

이미 같은 PC에서 최신 웹이 실행 중이면 중복 실행하지 않습니다. 인수인계 시점에는
`http://192.168.0.110:8790/` 웹을 진단용으로 남겼습니다. 운용 PC에서는
`http://127.0.0.1:8790/`을 사용합니다. `192.168.0.187`은 로봇 SSH 주소이며,
웹 주소에는 웹을 실행한 PC의 IP를 사용합니다.

시작만으로 위치 초기화나 임무가 실행되지는 않습니다. 먼저 준비 상태와 정지 응답을 확인하고,
일반 위치 확인·실제 초기 위치 입력·등록 Home 초기화 중 실제 위치에 맞는 절차를 선택합니다.
회전 시험이 성공해도 위치 수렴과 실제 정지를 별도로 확인한 뒤 병진 임무를 검증해야 합니다.


## 전원 재연결 후 정지 상태 재시험

2026-10-30 재시험에서도 병진·회전 명령을 보내기 전에 OpenCR 읽기 오류와
`turtlebot3_ros`의 `stack smashing detected`, 종료 코드 -6이 재발했습니다.
`benchmarks/physical_startup_20261030/stationary_retest_driver_failure.log`에 기록했습니다.
이번에는 필수 구동 노드 종료를 감지한 런치가 EKF, 센서 가드, motion mux, LiDAR 등
나머지 로봇 노드도 종료했습니다. PC 주행 런치도 정리했고 웹의 ESTOP을 유지했습니다.
실제 경유점 주행·마커 정렬·홈 복귀는 **미검증**입니다.

오류 전 정지 상태에서 읽힌 배터리는 약 10.99~11.03 V였습니다. 전압 저하,
OpenCR/모터 통신, 드라이버 결함 중 직접 원인은 아직 확정하지 않았습니다.
드라이버가 종료된 상태에서는 웹의 정지 확인 응답도 없어집니다. 이 상태를
위치 초기화 실패나 웹 버튼 문제로만 판단해서는 안 됩니다.

### 등록 홈 근처 배치 오차의 초기 가설 검증

정확한 등록 홈 한 점에서만 라이다를 대조하면 가까운 수동 배치 오차도 거부됐습니다.
등록 홈 반경 30 cm·헤딩 ±15도 내에서, 서로 다른 스캔 3개가 동일한 자유 공간 후보
주변을 반복해서 지지하는지 비동기로 검증하도록 보완했습니다. 기존 LOS 일치도 0.65,
차체 반경 22 cm의 알려진 자유 공간, 최신 입력과 실제 정지 조건을 유지합니다.
후보 위치를 실제 위치로 확정하거나 Home 좌표를 변경하지 않습니다. 기존 등록 홈에
넓은 공분산의 초기 가설을 입력할 수 있는 조건만 확인하며 이후 AMCL 수렴·정지
기준과 임무 출발 조건은 그대로입니다.

저장 스캔의 계산 시간은 약 0.13~0.18초였고, 3개 스캔의 반복 최소 일치도는 0.8125였습니다.
이번 실시간 정지 관측에서도 주변 일치 증거가 확인됐으나, 실제 초기 가설 발행 요청은
이미 구동 노드가 종료된 뒤라 정지 확인 응답 조건에서 거부됐습니다. 위치 초기화 또는
주행이 완료됐다는 의미가 아닙니다.

검증: 관련 회귀 검사 179개 통과, `smart_vision_amr` 패키지 빌드 성공.
이동·지도/Home 변경·오래된 스캔·중복 스캔·유효하지 않은 odom 입력은 증거를 무효화합니다.

SDK 및 vendor 센서 최신성의 오프라인 패치는 실차에 적용하거나 배포하지 않았습니다.
설치 SDK는 4.0.3이며 오프라인 SDK 패치는 다른 버전용이라 호환성이 확인되지 않았고,
자동 안전 검토가 추가 SDK 대조 작업을 보안 위험 가능성으로 거절했습니다.
미검증 패치는 작업 저장소 밖의 로컬 진단 폴더에 분리 보관했습니다.

## 전원 재투입 전 시작 조건 보강

이후 소프트웨어에서는 실차 웹의 새 임무·재개·홈 복귀를 최신 유효 배터리 메시지와
시험용 최저 전압 **11.2 V**로 제한했습니다. 로봇 안의 EKF 센서 가드도 같은 기준과
재설정 여유 0.2 V를 적용하며, OpenCR 읽기·쓰기 오류가 `/rosout`에 나타나면
즉시 비상정지를 잠급니다. 이 전압은 ROBOTIS의 차단 기준이 아니라 이번 실차
재시험을 위한 보수적인 임시 기준입니다. 실제 부하 전압을 기록한 뒤 조정해야 합니다.
**현재 기본값은 사용자 요청으로 10.8 V(3셀 LiPo, 3.6 V/셀)로 변경됐으며, 저전압
정지 후 재설정은 11.0 V부터 허용합니다.** 위 11.2 V는 당시 시험의 기록입니다.
10.97 V 부근에서 발생했던 OpenCR 통신 오류의 원인은 여전히 미확정이므로,
새 기준 이상이라는 사실만으로 구동 안정성을 보장하지 않습니다.
시작 전 검사도 3초 동안 구동 노드 유지, 원시 센서 시각 증가, 전압·발행자 상태가
연속으로 정상인지 확인하도록 바꿨습니다.

기존 로그에서 지도는 정상 로드됐습니다. `/map→base`가 없던 직접 이유는 AMCL에
초기 위치가 입력되지 않은 것이며, 이어서 구동 노드가 종료되어 위치 초기화에 필요한
정지 응답도 사라졌습니다. `/scan`은 처음에는 수신됐으나 일부 메시지가 TF보다
오래됐거나 큐에서 버려졌습니다. EKF 20 Hz의 50 ms 주기보다 긴 계산·스케줄 지연이
관측됐지만 mux·센서 가드에도 지연이 있어 EKF 주기만 낮추지 않았습니다.
위치 허용 오차와 지도 일치 기준도 완화하지 않았습니다.

**실차 재시험은 아직 완료되지 않았습니다.** 로봇 전원이 켜지고 배터리·OpenCR 연결이
유지된 뒤 새 코드를 양쪽에 반영하고, 차체를 움직이지 않은 채 이전 오류 발생 시점보다
긴 연속 관측을 통과해야 합니다. 그 다음 홈에서 후방 0번 마커를 확인하고 자세 초기화로
실제 `initialpose` 발행, AMCL 수렴, `map→base`, `/scan`, `/odom`의 최신성을 차례로
확인합니다. 모든 조건이 통과한 경우에만 짧고 열린 첫 경유점을 시험합니다.

로봇 런치만 켠 상태에서 PC의 별도 터미널로 아래 읽기 전용 검사를 먼저 실행합니다.
지난 오류는 정지 중 약 3분 48초 뒤에도 발생했습니다. 기본 관측은 5분이며,
이번 재시험은 요청에 맞춰 3분으로 실행합니다. 3분 통과만으로 과거 오류 시점까지
안정성을 확인했다고 볼 수 없습니다. 결과 JSON의 `status`가 `passed`일 때만
다음 단계로 진행합니다.

```bash
cd /home/kiki/Team2_workspace/src/SMART-VISION-AMR
source /opt/ros/humble/setup.bash
export ROS_DOMAIN_ID=16 ROS_LOCALHOST_ONLY=0 RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
python3 scripts/soak_robot_opencr_16.py --duration 180 --json-out "$HOME/smart_vision_logs/opencr_soak_after_reboot.json"
```

이 검사는 전압·원시 바퀴/IMU·라이다·EKF odom·OpenCR 오류·드라이버 노드를
관찰하고 ROS 명령은 발행하지 않습니다. 5분 통과도 실제 주행 성공을 보장하지는
않으므로 이어서 정지 상태 위치 초기화와 짧은 경유점으로 나누어 확인합니다.
